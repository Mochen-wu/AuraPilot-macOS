# 架构说明

## 1. 分层

```
┌─────────────────────────────────────────────────────────────┐
│ App（SwiftUI / AppKit，主线程）                              │
│   StatusBarController   MainWindowView   Overview/Lighting…  │
│        │ 观察快照                │ 调用命令                    │
│        ▼                        ▼                            │
│   AuraStore（ObservableObject，把后台快照搬到主线程）          │
└────────────────────────┬────────────────────────────────────┘
                         │ Snapshot / 命令
┌────────────────────────▼────────────────────────────────────┐
│ AuraController（核心门面，私有串行队列）                      │
│   • 状态与预设          • 帧定时器（30fps）                   │
│   • 传感器定时器（1Hz） • 去重下发 • 持久化（防抖 0.5s）      │
└───────┬──────────────────────────────────┬──────────────────┘
        │ ZoneFrame                        │ SensorSnapshot
┌───────▼──────────────┐        ┌──────────▼──────────────────┐
│ LightingEngine       │        │ SensorHub                   │
│  Effects（9 种纯函数）│        │  SystemSensorHub → AppleSMC │
└──────────────────────┘        │  SimulatedSensorHub         │
                                └─────────────────────────────┘
        │ ZoneFrame
┌───────▼─────────────────────────────────────────────────────┐
│ AuraTransport（可替换）                                      │
│  HIDTransport（IOHIDDevice，macOS 原生）                     │
│  RemoteBridgeTransport（HTTP → 另一台机器的 ACPI agent）      │
│  SimulatedTransport（演示，不动硬件）                        │
│        │                                                     │
│        ▼  FrameRenderer + ProtocolProfile(JSON)              │
│     字节流 → 设备                                             │
└─────────────────────────────────────────────────────────────┘
```

关键点：**引擎只算颜色，传输层只发字节**。二者之间只有 `ZoneFrame` 一个结构。
所以换硬件 = 换协议包或换 transport，引擎、UI、预设全都不用动。

## 2. 线程模型

| 位置 | 队列 | 说明 |
|---|---|---|
| UI | 主线程 | `AuraStore` 只在主线程被写 |
| 控制器状态、定时器、HID 写入 | `com.aurapilot.controller`（串行） | 所有可变状态只在这个队列上改 |
| 对外读 | `NSLock` 保护 `latest` | `snapshot` 随时可读，不做队列同步（避免死锁） |
| 回调 | `DispatchQueue.main` | `publish()` 统一派发，UI 不需要自己切线程 |

`log()` 用 `DispatchSpecificKey` 判断"是否已经在队列上"，避免自己给自己排队导致日志乱序。

## 4. 协议包（最重要的扩展点）

一个协议包描述"某种设备如何接收一帧灯光"。示例（内置 TUF 键盘包）：

```json
{
  "id": "asus-wmi-tuf-keyboard",
  "displayName": "ASUS TUF / ROG 键盘（WMI）",
  "vendorIDs": [2821],
  "zones": ["keyboard"],
  "frames": {
    "keyboard": {
      "name": "TUF 键盘 RGB",
      "channel": { "kind": "asusDeviceSet", "reportID": 0, "deviceID": 1048662 },
      "length": 6,
      "template": ["0xB4", "$mode", "$r", "$g", "$b", "$speed"],
      "modeCodes": { "off": 0, "solid": 0, "breathe": 1, "cycle": 2, "rainbow": 3 },
      "zoneCodes": { "keyboard": 0 }
    }
  }
}
```

模板里的占位符：

| 占位符 | 含义 |
|---|---|
| `$mode` | 当前模式码（查 `modeCodes`，缺省回落 static） |
| `$r $g $b` | 主色分量 0-255 |
| `$r2 $g2 $b2` | 次色分量 |
| `$brightness` | 亮度，按 `brightnessLevels` 量化（0 = 0-255 连续） |
| `$brightnessAsus` | `0x80 \| level`，ASUS 键盘背光专用 |
| `$speed` | 速度，按 `speedLevels` 量化 |
| `$zone` | 灯区码（查 `zoneCodes`） |
| `$sum8` | 前面所有字节之和的低 8 位（必须放最后） |
| `0xB4` / `B4` / `180` | 字面字节 |

通道三种：
- `hidFeature` / `hidOutput`：直接在本机通过 IOHIDDevice 写报告；
- `asusDeviceSet`：渲染成 `params` 数组，交给远程桥 agent 调 `DeviceSet(deviceID, params)`。

存放位置：`~/Library/Application Support/AuraPilot/protocols/*.json`，同名 id 覆盖内置。
首次运行会自动释放 `example-hid-aura.json` 作为模板。

## 4.3.1 设备选择（DeviceCatalog）

一台机器可能同时挂内置键盘（N-KEY 0x19B6 / usage 0xFF89）和外接 ROG 键盘
（Falchion 0x1B04 / usage 0xFF00，但只有 11B 的键盘输入口）。

- `DeviceCatalog.list()` 枚举所有 ASUS 接口，按「命中协议包 + feature 报告长度 ≥ 最小帧长」
  标注 `canControl`
- `AppSettings.preferredDeviceID`：nil = 自动打分；否则锁定 `0B05-19B6-338690048` 这类 id
- `HIDTransport(preferredDeviceID:)` 探测时把指定接口排到第一位，不在线则回退并记日志
- `AuraController.switchDevice(preferredDeviceID:)`：停定时器 → 关旧通道 → 重新探测 → 换通道 → 重推灯光
- 界面入口：诊断页「输出设备」卡片

## 4.4 多灯区一次提交（applyBatch）

Aura 固件是「写缓冲区 → SET 提交 → APPLY 生效」的模型，**缓冲区只有一份**。
若每个灯区各自跑一遍完整事务（亮度 → 灯效 → SET → APPLY），第二个灯区一 APPLY，
第一个灯区（键盘）就被覆盖 —— 这就是 v0.15「开了灯条/Logo，键盘不亮」的原因。

因此 `AuraTransport` 有 `applyBatch([ZoneFrame])`：

- HID 侧一次事务：**全局亮度(0x5A，只发一次) → 各灯区灯效(0x5D B3) → SET 一次 → APPLY 一次**
- 单个灯区写失败只跳过该灯区并记日志，不中断整批（机身可能没有灯条/Logo 硬件）
- 演示 / 桥接等通道沿用默认实现（逐帧 apply）

## 4.4.1 动画交给固件（FramePolicy）

`rogauracore` 的 `modeCodes` 含 breathe=0x01 / cycle=0x02，即固件自带灯效。
若仍按 30fps 逐帧下发，每个动画帧都要 SET + APPLY，而 APPLY 会让 N-KEY 的
HID 接口掉线重枚举 —— 表现为「点静态却狂闪」。

`FramePolicy.normalize(frame, baseColor, hardwareEffects)`：对硬件灯效设备把
动画帧主色固定为配置的基色，`dedupeKey` 逐帧相同，事务只在配置变更时下发一次；
软件动画设备（演示 / 桥接）保持逐帧。

亮度：`0x5A` 是整机共用的一条独立报告，没有按灯区之分，
`AuraController.setGlobalBrightness` 同步写入所有灯区。

## 4.5 自动开关灯光

「白天别亮、晚上自动开」由 `AutoLighting`（纯函数）+ `AutoLightingScheduler`（时机）两段组成：

- **判定**：`AutoLighting.decide(config, at:isDarkMode:)` 返回 `level`（0…1）。三种触发方式：
  按时间段（默认 18:00 → 次日 07:00，支持跨午夜与全天）、跟随深色模式、两者任一。
- **应用**：`AuraController.autoLevel` 只**缩放渲染时的亮度**，不写 `state`，
  所以白天压到 0 之后，晚上调回 1 就原样恢复，用户配置一次都不会被改乱。
- **手动优先（v0.18）**：白天 `autoLevel = 0` 会把用户改颜色/模式/预设的效果全吞掉，
  表现成「灯效界面所有按钮都没反应」。现在任何显式灯效操作都先走
  `AuraStore.markManualControl()` → `AuraController.setManualOverride(until:)`：
  立刻解除压暗，自动开关暂时让位到 `ManualOverridePolicy.expiry`（下一个
  18:00 / 07:00 边界）；`setAutoLevel` 在让位有效期内拒绝压暗，也不重发帧。
  界面提供「立即点亮」「恢复自动」两个出口，并在横幅上明示当前状态。
- **时机**：App 启动（先判定再启动引擎，开机第一帧就是正确亮度）、每 30 秒轮询
  （跨过时间边界）、`AppleInterfaceThemeChangedNotification`（深浅色切换）、
  系统唤醒。改配置时也会立即重判一次。
- **为什么不用 EC**：G-Helper 的「电池/唤醒/睡眠」开关写的是 ACPI-WMI，macOS 碰不到；
  这里纯软件实现，跨系统都能用，也不依赖固件。

## 5. 去重与省电

- 静态/关闭帧：`ZoneFrame.dedupeKey` 相同就跳过，避免每秒 30 次重复写 HID；
- 动画帧：固件自带灯效的设备（rogauracore 的 breathe / cycle）由 `FramePolicy.normalize`
  把主色冻结为基色，dedupeKey 逐帧相同 → 整个事务只在配置变化时发一次，动画交固件跑；
  只有无固件灯效的设备才逐帧下发；
- 系统睡眠 / 合盖：`NSWorkspace.willSleep` → `setPaused(true)`，唤醒后恢复并刷新传感器；
- 电池供电 + 打开"暂停动画"：60 秒一次检查电源状态（IOKit.ps），自动暂停输出。

## 6. 持久化

`~/Library/Application Support/AuraPilot/config.json`

```json
{
  "version": 1,
  "state": { "isOn": true, "zones": { "keyboard": { ... } } },
  "presets": [ ... ],
  "settings": { "engineFPS": 30, "quickColors": ["#FF7FA8", ...], "bridge": { ... } }
}
```

- 写入用 `.atomic`；
- 解码失败会把坏文件改名备份（`config.corrupt-<ts>.json`）再回落默认值，绝不因配置问题起不来；
- 所有新字段都有 `decodeIfPresent` 默认值，旧配置可直接升级。

## 7. 有意为之的取舍

| 取舍 | 原因 |
|---|---|
| 不用 SwiftUI `MenuBarExtra` | 无法稳定地在标题里显示实时温度；`NSStatusItem` 可控性更强 |
| 不用 Combine 贯穿核心 | 核心要能 `swift test`，用闭包观察者更轻，App 层再包 ObservableObject |
| 不做风扇写入 | 需要 root + EC 直通，ASUS 机器在 macOS 下不可达，做了就是假功能 |
| 灯效在 App 内算 | 设备固件模式有限；软件渲染才能做任意配色与速度 |
| 协议包用 JSON | 换机型不改代码，用户可自行校准 |
| 演示模式默认兜底 | 没硬件时 UI/引擎仍可完整跑通，开发与评审不被阻塞 |
