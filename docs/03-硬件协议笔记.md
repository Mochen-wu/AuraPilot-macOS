# 硬件协议笔记

> 这里的数值来自 G-Helper 源码（`app/AsusACPI.cs`）与 OpenRGB 的公开协议资料。
> 标注"待真机确认"的项，需要用 `aura-probe` 实测后在协议包 JSON 里改，不需要改代码。

## 1. ASUS ACPI-WMI（笔记本内置灯光的唯一通道）

### 1.1 两条入口

```csharp
const string FILE_NAME = @"\\.\\ATKACPI";          // 设备句柄 + DeviceIoControl
// 以及：
new ManagementObjectSearcher(@"root\wmi", "SELECT * FROM AsusAtkWmi_WMNB")
```

`DeviceSet(DeviceID, int Status)` / `DeviceSet(DeviceID, byte[] Params)` / `DeviceGet(DeviceID)` 是最小三件套。
`DeviceSet` 带 byte[] 时，会把参数打包成一个 `uint` 传进 WMI 方法（小端拼装），这就是为什么灯光参数最多 4 字节左右。

macOS 侧：无对应物，见 `01-可行性报告.md` 第 2 节。

### 1.2 灯光相关端点

| 常量 | 值 | 用途 |
|---|---|---|
| `TUF_KB` | `0x00100056` | 键盘 Aura 主通道 |
| `TUF_KB2` | `0x0010005a` | 备用通道（部分机型灯条/Logo 也在这里） |
| `TUF_KB_BRIGHTNESS` | `0x00050021` | 键盘背光亮度 |
| `TUF_KB_STATE` | — | 键盘灯电源状态（boot/awake/sleep/shutdown 位掩码） |
| `DevsCPUFan` | `0x00110022` | CPU 风扇（只读/写入曲线用） |
| `DevsGPUFan` | `0x00110023` | GPU 风扇 |
| `DevsCPUFanCurve` | `0x00110024` | CPU 风扇曲线 |

### 1.3 键盘 RGB 包（6 字节）

```
[0] 0xB4      命令字
[1] mode      灯效模式码（见下表）
[2] R
[3] G
[4] B
[5] speed     0-255
```

失败时 G-Helper 会改用 `0xB3` 再发一次到 `TUF_KB2`，然后再用 `0xB4` 补一次，作为兼容兜底。

### 1.4 模式码（与 `AuraMode` 对应）

| 模式 | 码 | AuraPilot |
|---|---|---|
| Static | 0 | `solid` |
| Breathe | 1 | `breathe` |
| Cycle | 2 | `cycle` |
| Rainbow | 3 | `rainbow` |
| Star | 4 | `star` |
| Rain | 5 | `rain` |
| Highlight | 6 | `highlight` |
| Laser | 7 | `laser` |
| Ripple | 8 | `ripple` |

`AuraMode` 的 rawValue 直接用这套数字，所以协议 JSON 里写 `"rainbow": 3` 就是设备码。

### 1.5 亮度包（1 字节）

```
0x80 | (level & 0x7F)      level: 0-3（4 档）
```

协议包里写作 `"$brightnessAsus"`，对应 `brightnessLevels: 4`。

## 2. USB HID（macOS 唯一原生可用通道）

### 2.1 设备发现

- 匹配 `VendorID = 0x0B05`（ASUSTeK）；
- Aura 控制接口位于**厂商自定义用途页**，但**不止一个页**（真机实测，见下表）；
- 外置 ROG 键盘/鼠标/耳机各自有多个 HID 接口，灯光接口往往不是键盘输入接口。

**真机实测（macOS 26，2026-11）**

| 设备 | PID | usage page / usage | feature 报告 | 是不是灯控口 |
|---|---|---|---|---|
| 内置键盘 N-KEY Device | 0x19B6 | **0xFF89 / 0x10** | **64B** | ✅ 是 |
| 外接 ROG Falchion RX LP | 0x1B04 | 0xFF00 / 0x01 | 11B | ❌ 否（键盘输入口） |

结论：**不能只匹配 0xFF00**，否则内置键盘永远找不到；但**也不能放任何不带用途页的
匹配条目**（见 2.1.1）。正确做法是把 `[0xFF00, 0xFF89]` 两个页都放进匹配字典。

`aura-probe devices` 会打印：

```
• N-KEY Device [0x0B05:0x19B6] usage=0xFF89/0x10 feature=64B
• ROG FALCHION RX LOW PROFILE [0x0B05:0x1B04] usage=0xFF00/0x01 feature=0B
```

判断灯控口最简单的办法：**feature 报告 ≥ 17B**（我们要发 17B 帧）。11B 那种是键盘输入口，
往上面发灯效帧不会报错，但灯不会动——这就是"全 OK 但不亮"的另一个分支。

### 2.1.1 macOS 26 的坑：匹配字典必须每个条目都带 usage page

`IOHIDManagerSetDeviceMatchingMultiple` 的数组里，只要出现**一个不带
`kIOHIDPrimaryUsagePageKey` 的条目**（裸 `[VID]` 或 `[VID+PID]`），整个
`IOHIDManagerOpen` 就返回 `0xE00002E2`（`kIOReturnNotPrivileged`）——
把同一批里本来能用的条目一起毒死。

真机对照实验：

| 匹配条目 | IOHIDManagerOpen |
|---|---|
| `[VID]` | ❌ 0xE00002E2 |
| `[VID + PID]` | ❌ 0xE00002E2 |
| `[VID] + [VID+page]` 混合 | ❌ 0xE00002E2（整批失败） |
| `[VID + page]` | ✅ |
| `[VID + PID + page]` | ✅ |

所以：**每个条目都要带 usage page**，需要多页就写成多条各自带页的条目。

### 2.2 报告写入

```swift
IOHIDDeviceSetReport(device, kIOHIDReportTypeFeature, reportID, bytes, length)
```

IOKit 语义：**reportID 非 0 时，缓冲区首字节必须是 reportID 本身**（macRogAuraCore 的
`messages[i][0]` 就是 `0x5D`，同时作为参数与缓冲区首字节传入）。`HIDTransport.write()`
负责拼接，协议包 template 里不写 reportID。reportID 为 0 时缓冲区不含 reportID。
部分设备只吃 `kIOHIDReportTypeOutput`，`HIDTransport` 支持两种（协议包 `channel.kind`）。

### 2.3 报文骨架（实验，需校准）

常见结构：64 字节 payload，首字节是命令字。

```
0xEC  0x40  <zone> <mode> <bright> <speed> <R> <G> <B> <R2> <G2> <B2> ... 补 0
```

- `0xEC`：Aura 命令族；
- `0x40` / `0x52`：初始/提交（不同控制器不一样）；
- 字段偏移因机型而异——这就是为什么本项目的协议包是 JSON，而不是写死在代码里。

**校准流程**

1. `aura-probe devices` 找到灯光接口；
2. 用官方软件（或在 Windows 上抓 USB）记录一次"切换成红色"的报文；
3. 把差异字段映射到 `$zone/$mode/$r/$g/$b/$brightness/$speed`；
4. 写进 `~/Library/Application Support/AuraPilot/protocols/<你的机型>.json`；
5. `aura-probe raw --hex "..."` 单步验证，再在 App 里应用到预设。

### 2.4 rogauracore 协议（内置键盘，已核对）

来源：[`black-dragon74/macRogAuraCore`](https://github.com/black-dragon74/macRogAuraCore)（BSD-3），
上游为 Will Roberts 的 rogauracore（Linux）。它证明了部分 ROG 笔记本把**内置键盘的
Aura 控制器**暴露成 USB HID 接口，macOS 可直接驱动。已知 PID：

| PID | 机型 |
|---|---|
| 0x1854 | GL553 / GL753 |
| 0x1869 | GL503 / FX503 / GL703 |
| 0x1866 | GL504 / GL703 / GX501 / GM501 |
| 0x19B6 | GA503 (Zephyrus G14 2021) |
| 0x1932 | ROG Strix Arion（M.2 盒） |

线路上的缓冲区为 **64 字节 = 1 字节 report ID + 63 字节 payload**（依据下面的描述符实测表）。
协议包 template 只描述前 16 字节的有效载荷，report ID 由 `HIDTransport.write()` 拼回首字节，
剩余字节补零到 64：

```
灯效帧 (report 0x5D)：B3 [zone] [mode] [R] [G] [B] [speed] 00 00 [R2] [G2] [B2] 00 ... 00
  mode: 0=静态  1=双色呼吸  2=色彩循环
  speed 查表（非线性）: {0xE1, 0xEB, 0xF5}
  多区效果时 zone=1...4，单灯效时 zone=0
亮度帧 (report 0x5A)：BA C5 C4 [0...3] 00 ...      （4 档，独立报告，同样补到 64B）
提交序列 (report 0x5D)：B5（SET）→ B4（APPLY），同样补到 64B
```

对应内置协议包 `mac-rogauracore-keyboard`：`frame.attached` 携带亮度帧、
`profile.commitFrames` 携带 SET/APPLY 序列、`speedValues` 实现速度查表。
`initFrames` 为空——macRogAuraCore 从不发握手帧。硬件效果只有 3 种，
彩虹/涟漪等由软件引擎逐帧下发。

**静态帧的坑**：`single_static` 里速度字节和副色三个字节都是 0，只有
`single_breathing` 才写速度码、双色标志 `[9]=1` 与第二色。我们把这条规则做成了
模板占位符 `$speedAnimated` / `$dualFlag` / `$r2Animated` 等，静态模式下自动渲染 0，
避免固件把"带垃圾字节的静态帧"判为非法而静默丢弃。

**报文长度与「设备打开方式」（真机两轮排查，2025-11 定案）**

`aura-probe descriptor` 解析 `kIOHIDReportDescriptorKey` 得到的真实声明
（ROG Strix 内置键盘 `N-KEY Device 0x0B05:0x19B6`，描述符 419 字节）：

```
ReportID 0x5A : input  5B / output  —  / feature 63B
ReportID 0x5D : input 31B / output 63B / feature 63B
ReportID 0xA5 : input  —  / output  —  / feature 16B
ReportID 0xC1 : input 16B / output 60B / feature 60B
ReportID 0xC2 : input 16B / output 16B / feature  —
kIOHIDMaxFeatureReportSize = 64（含 report ID）
```

两条实测事实：

1. **macRogAuraCore 在这台机器上能正常改颜色**（用户实测），它发的是
   **17 字节 Feature**、不补齐、不 open device。→ 17B 短包**有效**，
   63B 是描述符里的**上限**，不是必须长度。之前「必须补齐到 64B」的推断是错的。
2. 我们照抄 17B、但给每个接口都调用了 `IOHIDDeviceOpen` 时，`SetReport`
   返回 `kIOReturnSuccess` 而灯不响应。→ **差异点是 DeviceOpen**，
   现在 `HIDTransport.openDevicesOnProbe` 默认 `false`，与 macRogAuraCore 一致。

**APPLY 之后接口会掉线重枚举**：发完 `5D B4` 后该 HID 接口会从 USB 短时间消失，
旧 `IOHIDDeviceRef` 全部失效（后续 SetReport 一律 `0x10000003`，重新枚举时甚至
一度找不到设备）。因此一个事务必须「亮度 → 灯效 → SET → APPLY」连着打完，
失败时只能整体重打（`HIDTransport.apply` 的 `recover()`），不能只重试单条。

**EC 电源/电池策略在 macOS 上改不了**：G-Helper 里「唤醒 / 睡眠 / 开机 / 关机 /
电池」那一排勾，是通过 `DeviceSet(TUF_KB_STATE = 0x00100057, ...)` 写 **ACPI-WMI**，
最终落到 EC 固件。XNU 没有 ACPI-WMI 栈，DriverKit 也不支持，因此 macOS 既不能读
也不能写这些值。替代方案有两条：

- **在 Windows 里用 G-Helper 设一次**。这些值是 EC 持久保存的（EC 有独立供电），
  重启进 macOS 后依然生效，不需要每次重设。
- **macOS 侧软件模拟**：`AppDelegate` 监听 `willSleep` / `didWake` / 电源源变化，
  做「睡眠关灯、唤醒恢复、电池时暂停动画」。开机灯效由 EC 在 POST 阶段决定，
  系统还没启动，软件无法介入。

**接口选择**：同一 VID/PID 会暴露多个 HID 接口（键盘输入 / Consumer Control / Aura 控制），
macRogAuraCore 是对所有匹配接口广播。`HIDTransport` 同样广播（不 seize，避免吞按键），
只有全部接口都失败才算发送失败。

**扩展新机型**：`aura-probe devices` 枚举出新的 `0x0B05:xxxx` 后，把 PID 加进
协议包 `productIDs`（复制 JSON 到 `~/Library/Application Support/AuraPilot/protocols/`），
报文布局不同时再改 template。

### 2.5 Falchion（魔导士）外设协议（G-Helper AsusKeyboard.cs，待真机校准）

外置 ROG 键盘用的是**另一套协议**——这就是 macRogAuraCore 控制不了它们的原因
（它只会笔记本的 17 字节 feature report）。外设走 **output report 且设备逐包 ACK**：

```
Aura 包（output report）：
  [rid] 51 2C [mode] [chunk] [speed] [亮度%] [colorMode] [dir] 02
        R G B  R2 G2 B2  R3 G3 B3 ... 补 0 到包长
  mode: 0=静态 1=呼吸 2=色彩循环 3=反应 4=波浪 5=涟漪 6=星光 7=流沙 8=流动 9=雨滴 15=直控
  speed: 慢=255 正常=30 快=10（越小越快）
  colorMode: 0=单色 1=随机 16=双色交替（呼吸用）
保存板载存储: [rid] 50 55 （手动触发，不能跟帧发）
电量查询:     [rid] 12 01 → 应答 [6]=百分比 [9]=充电中
接口探测:     [rid] 12 00 → 真控制接口应答且 [5] != 0xFA（诱饵接口静默/NAK）
```

| 机型 | PID | report ID | 包长 |
|---|---|---|---|
| Falchion / Wireless | 0x193C / 0x193E | 0x00 | 65（含 ID） |
| Falchion RX / Ace / Ace HFX | 0x1B04 / 0x1A64 / 0x1B7E | 0x00 | 65（含 ID） |
| Falchion RX LP OMNI（矮轴） | 0x1ACE | 0x02 | 64（含 ID），接口 mi_02&col02 |

内置协议包 `asus-falchion-keyboard` 与 `asus-falchion-rx-lp-omni`（output report 通道）。
注意：RX 族的波浪/涟漪/流沙需要 02→01→00 分片序列，当前引擎用硬件静态 + 软件动画覆盖，
硬件分片待真机校准。macOS 侧 `aura-probe devices` 应能看到这些 PID 的 0xFF00 用途页接口。

## 3. AppleSMC（温度 / 转速）

### 3.1 访问方式

```swift
IOServiceGetMatchingService(kIOMainPortDefault, IOServiceMatching("AppleSMC"))
IOServiceOpen(service, mach_task_self_, 0, &connection)
IOConnectCallStructMethod(connection, 2 /* KERNEL_INDEX_SMC */, &input, size, &output, &outSize)
```

两次调用：`data8 = 9`（读 key info，拿 `dataSize`/`dataType`），`data8 = 5`（读字节）。

结构体布局（80 字节，与 smc.c 一致）：

```
UInt32 key;            // 4
Version vers;          // 6  (+2 padding)
PLimit pLimitData;     // 16
KeyInfo keyInfo;       // 12
UInt8 result, status, data8;  // 3 (+1)
UInt32 data32;         // 4
UInt8 bytes[32];       // 32
```

### 3.2 数据类型

| 类型 | 解码 |
|---|---|
| `sp78` | `Int16(bigEndian) / 256`（温度，℃） |
| `fpe2` | `UInt16(bigEndian) / 4`（风扇转速） |
| `flt ` | `Float32(bigEndian)` |
| `ui8 ` `ui16` `ui32` | 无符号整数 |

### 3.3 本项目使用的键

温度（取最高值，按顺序探测）：

```
Intel:       TC0P TC0D TC0E TC0F TC0H TC0J
Apple Silicon: Tp01 Tp05 Tp09 Tp0D Tp0H Tp0L Tp0P Tp0X Tp0b Tp0f Tp0j
GPU:         TG0P TG0D Tg0P Tg0D TCGC Tp0T
```

风扇：`FNum`（数量）、`F0Ac` `F1Ac` …（转速）。

Apple Silicon 上很多传统键不存在，探测不到就返回 `nil`，UI 显示"—"，**不会编造数字**。
诊断页会列出本次实际命中的键，便于判断机型差异。

### 3.4 为什么不做风扇写入

SMC 写入需要 root、需要 `AppleSMC` 的写权限，且写入的是 **Mac 自己的**风扇控制器——
写不到 ASUS 笔记本的 EC 上。所以曲线功能在本项目里明确不做。

### 3.5 灯光电源行为：固件管一半，系统管一半

G-Helper 的"灯光在 唤醒/电池/开机/关机时"设置（`AsusACPI.TUFKeyboardPower`）是一次性
写 EC 固件的持久开关：

```
DeviceSet(TUF_KB_STATE = 0x00100057,
          0xBD | boot(0x03<<16) | awake(0x0C<<16)
               | sleep(0x30<<16) | shutdown(0xC0<<16) | (0x01<<8))
```

**写成之后由 EC 固件在电源事件时自动执行，与操作系统无关**，因此：

- Windows 下用 G-Helper 设置过 → macOS 下同样生效，无需任何软件；
- macOS 原生改这个开关 → 不可达（ACPI-WMI）；走远程桥 agent 可调用同一 deviceID；
- **macOS 能自己做的是"系统负责"的那一半**（本 App 已实现，诊断页"电源行为"）：
  睡眠时下发熄灯帧（`NSWorkspace.willSleepNotification`）、唤醒恢复（`didWakeNotification`）、
  连接时初始化握手（协议包 `initFrames`）、电池供电暂停动画。对 HID 键盘（rogauracore），
  这些原本就是操作系统职责，macOS 有完整事件，行为与 Windows 无差别。

## 4. 远程桥协议（用于"Mac 控制另一台 ASUS 机器"）
### 4.1 接口

```
GET  /v1/aura/info
→ 200 {"id":"rog-g14","name":"ROG Zephyrus G14","vendor":"ASUSTeK","zones":["keyboard","lightBar"],"note":"Windows agent"}

POST /v1/aura/frame
← {"deviceID":1048662,"params":[180,3,255,79,135,128],"zone":"keyboard","mode":"rainbow"}
→ 200 {"ok":true}
```

- `deviceID` 十进制，`1048662 == 0x00100056`；
- `params` 就是 `DeviceSet(deviceID, byte[])` 的字节数组；
- 可选 `Authorization: Bearer <token>`（配置里填 token 即启用）。

### 4.2 agent 侧实现要点

Windows：直接调用 G-Helper 的 `AsusACPI.DeviceSet(deviceID, params)`。

```csharp
var acpi = new AsusACPI();
acpi.DeviceSet((uint)req.deviceID, req.params, "AuraPilotBridge");
```

Linux：`/sys/class/leds/asus::kbd_backlight/` 或 `asus-wmi` 暴露的 Aura 接口，
写法取决于机型与内核版本。

### 4.3 延迟与频率

30fps 动画对 HTTP 来说偏重（每帧一次请求）。若要做动画，建议 agent 端支持
`POST /v1/aura/stream`（长连接 + 批量帧），或干脆让 agent 自己按模式跑动画，
Mac 端只下发"模式 + 颜色 + 速度"这类低频参数。
